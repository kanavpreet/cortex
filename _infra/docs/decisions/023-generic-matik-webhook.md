# Generic Matik Webhook Framework (OpsBot Incident-Channel-Summary Feed)

Date: 2026-07-16

Status: `accepted`

Related: [013-chronicler-direct-kafka-python.md](013-chronicler-direct-kafka-python.md), [016-chronicler-kafka-consumer.md](016-chronicler-kafka-consumer.md), [020-jira-webhook-spoofing-mitigations.md](020-jira-webhook-spoofing-mitigations.md)

## Context

We want Matik to hold a running LLM summary of an incident's Slack channel, generated by **OpsBot** (Airbnb's existing incident-ops Slackbot) rather than a native Incident.io workflow — Incident.io's workflow/nudge builder has no callable action for LLM-summarizing a Slack thread; that capability only exists inside its built-in nudge feature. See the design doc (Slate `LFCYyiXBOB`, ticket ITE-797334) for the full rejection rationale and product framing.

OpsBot needs a way to push its summary into Matik. Every existing Chronicler provider (GHE, Jira, Incident.io) has its own bespoke transformer, signature scheme, and one-provider-per-onboarding relationship with Yoyo's `external_service_type` registration. That per-vendor cost doesn't make sense for a webhook Matik itself defines the contract for — we don't need to reverse-engineer someone else's signing convention, and we anticipate more first-party, Matik-originated event sources beyond this one summary feed.

## Decision

**Add one new generic provider, `matik`, rather than a bespoke `opsbot` provider.** A `category` field in the payload discriminates sub-use-cases (`incident_channel_summary` is the only one today) so future first-party event sources reuse the same provider registration, transformer, topic(s), and signing secret instead of a new `#api-infra` round trip each time.

**Signature: raw HMAC-SHA256**, header `X-Matik-Signature-256`, mirroring the GitHub transformer's `X-Hub-Signature-256` construction — not Incident.io's Svix scheme. Since we originate this webhook ourselves, there's no vendor convention to inherit. Secret is `chronicler.generic_webhook_secret` in secret-lair, exposed as `ChroniclerConfig.generic_webhook_secret`, and shared with OpsBot via a separate vault grant (OpsBot signs outgoing requests with the same secret).

**Payload envelope:**
```json
{
  "category": "incident_channel_summary",
  "source": "opsbot",
  "entity_id": "INC-1234",
  "generated_at": "2026-07-14T18:32:00Z",
  "data": {"summary": "<single-paragraph LLM-generated summary>"}
}
```
`entity_id` is the Incident.io **reference id** (e.g. `INC-1234`), not the internal `incident_id`.

**Registered `external_service_type`s** (via `#api-infra`; see [chronicler.md](../development/chronicler.md#onboarding-a-new-webhook-provider)):
- `matik_generic_webhook_events` — production (staging shares this; no separate staging registration)
- `matik_sandbox_generic_webhook_events` — sandbox

Both tokenize to provider `matik` via the distinct `generic` token in `CallbackEvent.provider` (every `external_service_type` is prefixed `matik_`, so a bare `matik` token would ambiguously match every provider).

**Storage (updated 2026-07-20 — see note below): two columns on the existing `incidentio_incidents` table**, named after the data rather than the producing tool (so they survive OpsBot being replaced or renamed):
- `incident_channel_summary` — the AI/LLM-condensed summary (produced by the Enricher), the value served to the MCP. Named plainly with no `_llm` suffix, matching the existing `root_cause_summary`/`description_summary` convention where the LLM output itself owns the plain column name.
- `incident_channel_summary_hash` — change-detection hash, mirroring the existing `root_cause_summary_hash` / `description_hash` pattern.

The raw OpsBot channel-summary text is **never persisted** — it only ever exists inside the Enricher's SQS `EnrichmentRequest.content`, discarded once the LLM call returns, exactly like Incident.io's own raw `summary`/`resolution_statement` fields. *Note: the original design (and its first implementation) instead added a third column — a raw `incident_channel_summary` receptor written via a partial `UPDATE`, plus `incident_channel_summary_llm` for the LLM output — with the raw write raising `BaseRecordNotFoundError` (so Scribe retries) if the base incident wasn't ingested yet. Code review flagged that as inconsistent with the no-raw-storage precedent above, so the raw column and its `base_message_model`/`base_partial_update`/DAO write path were removed (this source is now enrichment-only, like Incident.io), and the LLM column was renamed from `incident_channel_summary_llm` to the plain `incident_channel_summary` once the raw column's name was freed. The same not-yet-ingested retry behavior now happens on the enrichment write path instead (`update_llm_fields_from_message` returns `False` → `BaseRecordNotFoundError`).*

Both columns are excluded from the regular Incident.io ingestion path's `update_columns` (see `common/datasources/incidentio.py`'s `exclude_columns`) so a routine incident re-upsert can never clobber or NULL them. The `incident_channel_summary` `DataSourceSpec` (`common/datasources/incident_channel_summary.py`) owns writing to them via its enrichment route only, reusing `IncidentIOIncidentDAO` (bound to its own spec via a `source_type` constructor parameter) rather than a new DAO class, since both sources share the one table.

## Consequences

- **`base_message_model` / `base_partial_update` extension point added to `DataSourceSpec`/`GenericHandler`, then unused here.** Originally exercised by this source for the raw-receptor partial write; removed once the raw column was dropped (see Storage note above). The extension point itself remains available in the registry for a future source with that patch-only, no-insert shape — it's just not exercised by this feed today.
- **One provider serves multiple future categories.** Adding a second Matik-originated event type is a `category` value + a new Scribe `source_type`/DAO method, not a new provider transformer, Yoyo ticket, Kafka ACL request, or secret.
- **`/v1/enrichment/hashes` and `/v1/enrichment/hashes/batch` gained a fourth source_type branch** (`incident_channel_summary`, keyed on `reference_id` rather than `incident_id`) — these endpoints hand-list columns per source_type rather than deriving them from the registry; a future generic-webhook category needs its own branch here too until that endpoint is refactored to read `DataSourceSpec.llm_columns` directly.
- **No separate staging `external_service_type`.** Staging's Chronicler consumer shares the production topic (consistent with how all environments already consume the same GHE/Jira/Incident.io topics via per-env consumer *group_id*, not per-env topics).
- **Deploy/verification is out of scope for this ADR's authoring PR** — end-to-end testing (sandbox webhook round-trip, Enricher pipeline, MCP surfacing) requires OpsBot-side work outside this repo and is tracked separately.

## Out of scope (explicitly deferred)

- **OpsBot's Phase 2** (15-minute re-summarize loop, delta-only updates to the existing correlation Slack thread) is entirely OpsBot-side; the ingestion path built here already supports repeated webhook deliveries (each re-triggers enrichment via a hash comparison the Enricher computes over the incoming raw text — no raw column is overwritten, since none is stored).
- **Flagging a summary as an unreviewed background draft** vs. one the IC filled in via the existing 30-minute nudge workflow — open question, not addressed by this storage design.
- **Refactoring `/v1/enrichment/hashes` to be registry-driven** — the four-branch `_dispatch` function works today but doesn't scale cleanly; deferred until a second generic-webhook category or a fifth source_type makes the hand-listing cost more visible.
